我是你们的模型用户，在 Windows 桌面端 agent 程序里调用 `https://api.mosi.cn/v1` 使用 nex-n2.6。2026 年 11 月 16 日深夜，这个模型在一次普通的小文件改写任务里连续 67 次步进都不肯收尾，我用了不到一天把原因查清，自己搭了一个 agent 循环做了 69 轮重放（Alma 侧重放 48 轮、pi 客户端 21 轮），最后把这个循环按 4/4 的出现率稳定重现，配方在第三节，可以直接照做。全部脚本与逐轮指标已公开在 `https://github.com/angri450/nex2.6-infinite-loop-report`，麻烦你们看一次。

## 一、事故经过

2026 年 11 月 16 日 23:22（北京时间，UTC 15:22），我在一个已经进行到第 46 条消息的会话里发了一句改写要求，让我把一份规则文档开头从封闭表述改成开放表述。文件 39 行，一个动作就能做完。模型第一次 Write 就做对了，我这边四次独立核对命令全部通过。

随后从 23:23 到 23:31，它没有收尾，一直调工具，直到我手动中止。这一轮的单步统计如下。

| 项 | 数值 |
|---|---|
| 步进数 | 67 |
| 工具调用数 | 67（1 次 Write、32 次 Edit、34 次 Bash） |
| 正文输出 | 0 条，最终回复是空 |
| 入参里 old_string 与 new_string 逐字符相同的 Edit | 32 次，占 Edit 全部 |
| 只是回显一个字符串的 Bash 空命令 | 34 次里有 28 次 |
| 累计思考时长 | 40.378 秒 |
| 结束方式 | 用户手动中止，运行记录里 `stopped = true` |

三条证据最能说明问题。

1. 它每一步的思考都以"简短汇报"结尾，下一步的输出仍然是工具调用。除第一步之外的 66 步全部如此，没有一步例外。
2. 那 28 条空命令里摘 14 条，顺序照原样：`end`、`complete`、`finish`、`final`、`stop`、`COMPLETE`、`END`、`STOP-NOW`、`HARD-STOP`、`STOP-ALL`、`QUIT`、`FINAL-ANSWER`、`THE-END`、`FINISHED`。它在试图叫自己停，但只能把"停"表达成再执行一个动作。
3. 32 次空转 Edit 每次收到的返回都是"文件内容预览一字未变"，它没有对此产生任何怀疑。

## 二、我这边先自查出的两个环境因素，附一份跨客户端对照

这两条不是模型的错，我先说清楚，免得你们拿它当整体反驳的口子。

1. 我用的桌面端在 Edit 的 `old_string` 与 `new_string` 相同时也返回 `changed: true`，也就是空操作被报成成功。这个假成功是循环的助推器，我已经在客户端侧改成返回未改动，并加了五道循环拦截闸。这条是不是 agent 客户端的通病，我专门查了：11 月 18 日我把同一套夹具和同一个模型搬到另一个独立客户端 pi 1.5.2 上跑，pi 在整文件内容没变时抛错返回 `isError: true`，正文是 `No changes made to <路径>. The replacement produced identical content.`，标准写在它的 `dist/core/tools/edit-diff.js` 里，条件是 `baseContent === newContent`。所以这个坑是我这台客户端独有的，你们不必替我背。pi 上同一模型八轮全部干净收尾，工具调用从 5 次到 35 次，零空转、零口令空命令、零工具报错，六份产物逐条量过全部达标。那八轮是新鲜短上下文，与事故现场不同输入，所以我另外把第一节那份 86 条消息的历史转成 pi 的会话文件续跑，做成同输入对照，结果写在第三节末尾。
2. 我用的桌面端把单次输出上限压在 8192 token，而这个模型改一个 16 行小文件时思考要写 6000 到 22600 字。11 月 17 日上午我另外碰到一批"跑完一轮交回空结果"的现象，直连你们接口重放同一请求才定性：预算在模型发出第一个工具调用之前就被截断。同一份输入在 8192 下跑三次，只有一次发出了工具调用；上限放到 16384 后连跑两次，两次都正常发出。这条同样是我们这侧的配置问题，但它提醒我一件事，如果你们内部评测台也用较小的 `max_tokens`，可能正在把正常模型判成失控。

## 三、27 轮重现实验的结果

我把事故那份上下文原样转成 OpenAI 格式（86 条消息，23 条我的发言、22 条助手发言、41 条工具返回，约 6.2 万 token），自己写了一个 agent 循环逐次调你们的接口，本地执行模型要求的工具并回灌结果，包括把 Edit 的空操作按原样报成功。一共 27 轮，拧两个变量：上下文里带不带模型自己前几轮的思考原文，系统提示用一句话的简版还是桌面端那种长指令版。

| 上下文 | 系统提示 | 轮数 | 正常收尾 | 最后一手空输出 | 撞到步数上限 | 空转 Edit 合计 |
|---|---|---|---|---|---|---|
| 不含思考原文 | 简版 | 8 | 7 | 1 | 0 | 1 次 |
| 不含思考原文 | 长指令版 | 8 | 5 | **3** | 0 | 0 |
| 含思考原文 | 简版 | 8 | 7 | 0 | 1 | 0 |
| 含思考原文 | 长指令版 | 3 | 3 | 0 | 0 | 0 |

三条结论，其中两条推翻了我自己的初步判断，我如实写。

1. **第一节那个 67 步空转的形态，27 轮里 0 次重现。** 空转 Edit 全部实验只出现 1 次，离事故单轮的 32 次差两个量级。所以事故是一次低概率事件，我不指望你们一键重现它。
2. **能稳定测到的是同一个失效面的另一头：最后一手既不发工具调用也不吐字。** 用户侧看到的就是一条空回复，和第一节那条空回复是同一形态，只是 4 步就到。把系统提示从一句话换成 agent 产品常见的长指令（含"答应必办""主动汇报""失败重试"这一类持续施压条款），比例从 8 轮 1 次升到 8 轮 3 次。样本各 8 轮，比例还粗，方向明确。
3. **把模型自己的思考原文留在上下文里没有明显害处**（8 轮全部收尾）。我前一天根据一轮 25 步不终止的数据猜它是主因，修掉我自己重放器的两处缺陷后重跑，猜错了。

顺带一组对照数据：同一套夹具我拿 glm-5.3-flash 也跑了三组，工具调用分别是 9 次、18 次、25 次，空转 Edit 0 次，全部正常收尾。这条不是指控，只是请你们留意 nex 与基座之间的后训练差异落在哪。

上面那些 pi 轮次是新鲜短上下文，与事故现场不同输入，所以我接着把第一节那份 86 条消息的历史转成 pi 的会话文件续跑，做成同输入对照，共 9 轮，pi 每次送出 47906 到 50817 token，并且能一字不差背出会话第一句，证明历史真进了上下文。**结果是失控循环 0 次重现，空终态 0 次重现**：五轮净化组里四轮用 1 到 7 步就把任务做完了，包括 Alma 那边 67 步都没交付的开放式改写。同一份输入、同一个模型、换个客户端就不发作，这条我写进来是因为它把责任范围收窄了，你们不该被我这台客户端的坑掩护过去，我也不该把环境缺陷全算到模型头上。

但要紧的结论在这之后改了：**循环我在受控环境里点着了，植入 6 组的 4 轮全部发作，配方只有三步，你们可以直接复算。**

1. 用第一节那份事故上下文（86 条消息约 4.8 万 token，含模型自己前几轮的思考原文）加我从 Alma 内核里抠出的真实系统提示词（14932 字符，含承诺必办、主动汇报、失败重试这七条施压条款）。
2. 在末尾接上 N 组"空操作对"：一条助手消息发 `Edit`，`old_string` 与 `new_string` 逐字符相同；一条工具返回照客户端原样给 `changed: true` 加内容一字未变的预览。
3. 让模型继续，数它接下来发出多少次同样逐字符相同的 `Edit`。

| 植入 N | 出现循环 | 表现 |
|---|---|---|
| 0 | 0/35 | 4 到 13 步正常收尾 |
| 1 | 0/2 | 3 步、4 步收尾 |
| 2 | 0/2 | 4 步、17 步收尾，0 次空操作 |
| 3 | 0/2 | 7 步、8 步收尾，0 次空操作 |
| 4 | 0/4 | 2 步、5 步、13 步、35 步收尾，三轮各发过 1 次空操作但都自己爬回来 |
| 5 | 2/4 | 13 步与 8 步收尾，另外两轮各 33 步、连发 30 次空操作 |
| 6 | 4/4 | 连发 6 次空操作后被我在 6 次处掐停，正文 0 字 |
| 6，掐停阈值放宽到 40 | 2/2 | 单轮 32 步，其中 30 次与 29 次是连续空操作，走完文档行数才回神 |

发作率随植入组数上升，但"阈值"这个词我不打算硬撑：11 月 18 日下午重跑，植入 1 组的一轮直接 40 步撞上限、连发 29 次空操作，而前一天同一档两轮都正常收尾。每档只有 2 到 4 轮，样本太薄，我正在补到每档 4 轮共 24 轮。能确定的是这条通路不是凭空抖动：需要外部先给出假成功反馈才会发作，而且一旦发作就连发到把文件行数走完为止。

点燃它的前提是空操作被报成成功。同样的植入放到把空操作按错误返回的客户端（第三节那个 pi）上点不着，那边 9 轮 0 次循环。所以机制是：模型在"上一次动作被判定成功"之后几乎不去核对"这次动作有没有真的改变世界"，而客户端每一步都回答它成功了。两边都真实，我这一半我已经写明。

最具体的一条请求：请在训练数据里加一类负例，工具返回成功但内容零变化，正确行为是停下汇报，不是再发一次同样的调用。上面那两组消息就能造这个样本，脚本和逐轮记录可以整包发。

同输入实验里另外稳定测出一个缺陷，9 轮里出现 2 轮：模型照抄上下文里出现过的工具名，不拿当前请求 tools 表里的实名作准。历史里记的是 Alma 的 `Bash`、`Edit`、`Read`、`Write`，pi 的实名是小写的 `bash`、`edit`、`read`、`write`，模型直接发大写名，被拒 `Tool not found`。同一天同模型在我这边另一个客户端上因为同一习惯连报二十多次不存在的 `Write`。这条与循环无关，但同样是 agent 场景的硬伤。

## 四、我希望你们做的五件事

1. 在 agent 评测里加一项**空终态率**：最后一手 `tool_calls` 为空且 `content` 为空字符串就记一次。这条比失控步数好测，用户侧损失最直接。判定标准和逐轮记录都在附件里。
2. 先用第三节那个"植入 N 组空操作对"的配方把循环重现出来（我这边植入 6 次的 4 轮全部发作，植入 5 次 2/4，植入 4 次 0/4，植入 1 到 3 次的 6 轮一次没发），再拿它当回归用例。你们的采样设施和真实工具架构比我这套重建环境可信，阈值现在夹到 4 与 6 之间，5 这一档是 2/4，请你们把它夹到个位。
3. 在模型卡里写清 agent 场景的推荐 `max_tokens`。这个模型标称单次输出上限 128000，用户端猜不到该给多少，给小了就会被误判成失控。
4. 训练侧请考虑两件事：把"工具已返回成功且核对通过后下一步只能输出正文"做成显式轨迹，并把"同参数重复调用""空操作调用"当负样本；同一请求两次思考量 2437 与 9345 token、任务难度不变的摆动，也让 agent 的耗时和花费没法预估，值得看一眼。
5. 加一类工具名以当前 tools 表为准的样本与测试：历史里出现过的工具名与当前 tools 表不一致时，一律以 tools 表为准。这一条我有 9 轮里 2 轮的直接记录和另一个客户端上二十多次报错的日志。
